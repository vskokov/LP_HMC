# Operating the LP_HMC GPU campaigns on Hazel — instructions for a Claude Code agent

You run on a login node of the NCSU Hazel cluster, which uses Slurm. Your job is to keep the GPU campaigns of this repository running correctly. That means submitting them, monitoring them, diagnosing failures, and making the routine corrections listed below. Escalate everything else to the user.

You are an operator, not the analyst. Physics decisions belong to the user and to the analysis on the workstation: which points to run, and what a result means. Read `CLAUDE.md` (code rules), `docs/HPC.md` (mechanics), and **`docs/HPC_RUNPLAN.md`** before acting. The run plan is the only authority on which stages to run; it is updated from the workstation through `git pull`. Run only the stages it marks ACTIVE, and never those marked LOCAL or HOLD.

## 0. Context in one paragraph

The code samples a 3D lattice φ⁴ theory with a `(∇²φ)²` term, using HMC and replica-exchange umbrella sampling in a quadratic Fourier-space collective variable (`scripts/cv_umbrella.jl`).

Each *run* is one directory with:
- `checkpoint.jld2`
- `statistics.csv`
- `diagnostics.json`
- `complete.json` once finished

Each run belongs to a *stage* and is listed in `$LP_HMC_RUNS/cv_umbrella/<stage>/manifest.csv`. Stages: `validate`, `uline`, `s2_zm2`, `s2_zm1172`, `lro`.

On Slurm, every run is a chain of ≤2 h jobs, generated by `scripts/slurm_backend.py`. The simulation stops after `CVU_RUNTIME` seconds, saves its checkpoint, and exits 75. The job script then resubmits itself.

Results are copied to the workstation (without checkpoints) and analysed there.

## 1. Environment, every session

```bash
cd <repo>                                  # the clone on the cluster, branch phase-diagram-paper
export LP_HMC_RUNS=/share/$GROUP/$USER/lp_hmc_runs    # ask the user if this differs
module load python 2>/dev/null || true     # need python3 with numpy, scipy, pandas
git pull --ff-only                         # pick up fixes and run-plan revisions
cat docs/HPC_RUNPLAN.md                    # which stages are ACTIVE (check the revision number)
```

`LP_HMC_RUNS` must be set identically in every shell. Manifest paths are absolute and derived from it.

## 2. Routine loop

Run this every 1–2 hours. Use `/loop` if it is available.

```bash
python3 scripts/cv_campaign.py status --stage <active stages>
squeue --me --format="%.10i %.45j %.8T %.10M %.12l %R"
```

For every row that is **IDLE**, meaning not complete and with no job queued or running:

1. Read the newest log in `<run>/slurm/*.out` (`ls -t <run>/slurm/*.out | head -1`), and `<run>/diagnostics.json`.
2. Classify the failure with the table in §3 and apply the matching action.
3. Restart chains with `python3 scripts/cv_campaign.py submit --stage <stage> [--gpu TYPE]`. This is idempotent: it only starts rows that are incomplete and not queued.
4. Record what you saw and did in the journal (§6).

Also check these on every pass:

- **Progress.** `sweeps` (thermalization) or `collected` (production) in `diagnostics.json` must increase between passes for every active run.
- **HMC acceptance.** `hmc_acceptance_mean` should be 0.65–0.90.
- **Swap acceptance.** During thermalization, `min_swap` should be ≥0.2 for the umbrella stages. The `lro` stage has κ=0 and no swaps, so it is exempt.
- **Quota.** Check disk usage of `$LP_HMC_RUNS` with `du -sh` and the cluster quota tool. Checkpoints for L=32 are a few hundred MB each.

## 3. Diagnosis and permitted corrections

| Symptom | Likely cause | Action (permitted without asking) |
|---|---|---|
| Log ends `exit=75` but no follow-up job in `squeue` | `sbatch` from the compute node failed (transient) or the chain was cancelled | `submit` the stage again |
| `exit=3`, log says "transport gate not met by max sweeps" | Thermalization reached `CVU_MAX_THERM` before walkers made round trips | If `round_trip_walkers` and `min_swap` are still rising (compare with the journal), raise `CVU_MAX_THERM` for that row in the manifest by ×1.5, at most twice, then `submit`. The checkpoint resumes. If they are flat, **escalate**: the ladder needs redesign. |
| `ERROR: checkpoint ladder mismatch` / `parameter mismatch` | The manifest row was changed in a ladder field (`CVU_WINDOWS`, `CVU_SMIN/SMAX`, `CVU_KAPPA`, `CVU_POWER`, `CVU_M2`, `CVU_KIND`, `CVU_SHELL_Q`) after the run started | Restore the original values (git or the journal). Never delete the checkpoint to "fix" this. |
| `hmc_acceptance_mean` < 0.6 or > 0.92 **during thermalization** | Step size not suited | Scale `CVU_EPS` in that row by 0.85 (low acceptance) or 1.15 (high), and keep `CVU_NLF·CVU_EPS` ≈ 1 by adjusting `CVU_NLF`. HMC stays exact for any ε. Do **not** change ε once `phase` is `collect`; escalate instead. |
| CUDA error, `CUDA_ERROR_*`, `illegal address`, node-specific crash | Bad node or driver | Resubmit. If the same node fails twice, add it to `"exclude"` in `configs/hpc/hazel.json` (comma list) and resubmit. |
| `Out of memory` / `oom-kill` (host) | `--mem` too small | Set `"mem"` in the config to `"32G"` and resubmit. |
| GPU out of memory | Lattice too big for the GPU type | Use a larger GPU with `--gpu a100`, `l40s`, `h100` or `rtx_6000_pro` |
| Julia precompile / `Pkg` errors, missing module | Environment | Rerun `python3 scripts/slurm_backend.py selftest`. Fix `"modules"` in the config per `module avail`. Never edit `Project.toml` / `Manifest.toml`. |
| Jobs pending > 6 h with reason `Resources`/`QOSGrpGRES` | Chosen GPU type busy or capped | Check `si --gpus`. `scancel` the pending jobs of that stage and `submit --gpu <other type>`. Switching GPU type mid-chain is allowed; record it. |
| Run killed at walltime (`TIME LIMIT`, `DUE TO TIME LIMIT`) with no `exit=` line | Startup + budget exceeded 2 h | Lower `"runtime_minutes"` in the config (e.g. 100 → 90), then resubmit. The checkpoint from the last save is used. |
| `continuation cap 400 reached` | Run far longer than estimated | **Escalate** with the elapsed and remaining estimate |
| `statistics.csv` row count ≠ `collected × windows` (+ header) | Should never happen; resume truncates automatically | **Escalate**. Do not edit files. |
| Same row fails 3 times in a row for an unclassified reason | — | Stop resubmitting that row and **escalate** with the log tail |

Edit manifests directly in the CSV, and only in the fields named above. **Do not run `prepare`** for a stage that has runs in progress. It regenerates the manifest from code and silently discards your edits. Run `prepare` only for a stage that has never been submitted, or when the user asks.

## 4. Never do these

- Delete or overwrite `checkpoint.jld2`, `statistics.csv` or `complete.json`. Never `rm -r` a run directory. To restart a run from scratch, create a new run with a new seed, which means a new directory, and only when the user agrees.
- Change the physics of a started run: `CVU_Z`, `CVU_M2`, `CVU_L`, `CVU_KIND`, the ladder, `CVU_SAMPLES`, `CVU_SKIP`. A higher `CVU_SAMPLES` before completion is the one exception, and needs user approval.
- Add stages, masses or lattice sizes, or start runs beyond the ACTIVE stages in `docs/HPC_RUNPLAN.md`.
- Touch the files listed under "What NOT to touch" in `CLAUDE.md`, or add dependencies.
- Change `src/` physics code, force/HMC kernels, or `cv_umbrella.jl` semantics. Bug fixes in the Python drivers (`slurm_backend.py`, `cv_campaign.py`) are fine if they don't change what is simulated. Commit them (§6).
- Use other partitions, QOS, or long walltimes than in `configs/hpc/hazel.json` without asking. Exclusive or multi-GPU jobs are also off limits without asking.
- Push to `main` or force-push anything.

## 5. Acceptance checks you can run on the cluster

**Validation stage** (before any production):

```bash
python3 scripts/analyze_cv_umbrella.py --dir $LP_HMC_RUNS/cv_umbrella/validate/Zm2/L12 --bootstrap 40
```

Compare with the workstation reference:

| Quantity | Reference |
|---|---|
| `m_eq` | −1.7297 ± 0.0039 |
| `barrier` | 1.261 ± 0.056 |
| `latent_q` | 0.0297 ± 0.0004 |
| `deff_ordered` | ≈ 1.04 |

Pass if every |difference| ≤ 3·√(σ₁² + σ₂²), and the HMC acceptance is 0.75–0.85 at L=12. On failure, do **not** start production; escalate with the numbers.

**Per finished `uline` run** (cheap sanity check, optional):

```bash
python3 scripts/cv_to_schema3.py      # converts completed uline runs for the transition-order analysis
```

The full analysis runs on the workstation.

## 6. Journal, commits, escalation

- **Journal.** Append one entry per pass that saw or changed anything to `$LP_HMC_RUNS/OPS_JOURNAL.md`: UTC time, stage/run label, observation (numbers), action, outcome. Before every manifest edit, record the field, its old value and its new value. This file is how the user and the workstation agent learn what happened.
- **Commits.** Commit driver fixes and config changes (`configs/hpc/hazel.json`) on a branch `hazel-ops` and push it there (`git push -u origin hazel-ops`). Manifests live under `$LP_HMC_RUNS`, not in git; the journal covers them.
- **Escalate.** Stop, write the journal entry, and tell the user plainly when any of these happen:
  - validation fails;
  - a row hits the cases marked **Escalate** above;
  - more than 25% of a stage's runs fail in one day;
  - a run-plan revision is ambiguous, or conflicts with runs already in progress;
  - anything suggests the data are wrong rather than slow.

  The last case includes a NaN in `diagnostics.json`, acceptance collapsing in the middle of collection, or ordered- and disordered-start runs of the same point drifting to visibly different `M` distributions.

## 7. Reporting

When asked for status, give for each stage:

- how many runs are complete, running, pending and idle;
- per running run: phase, sweeps or collected out of target, and the rate per day;
- an ETA;
- every correction made since the last report, taken from the journal.

Report numbers, not impressions. If you have not verified something, say so.
